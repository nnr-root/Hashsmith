# WP2.2 (PBKDF2-SHA1 AVX2 compression gap) — feasibility spike, not an implementation

## Why a spike, not a build

The AVX2 compression core for SHA-1 already exists
(`internal/smith/sha1avx2_amd64.s`, generated by `sha1avx2_gen.py`) and still
loses to Go's stdlib `crypto/sha1` by a real margin. A prior session's own
retrospective left this explicitly open and unchosen, flagging it as harder
than SHA-256/512's wins. This session's job was to measure where the time
actually goes and look for a concrete, cheap idea — not to commit to a
rewrite — per this project's own standing discipline (the scrypt-AVX2 spike
is the precedent for "measure before building").

This machine (Apple M2, arm64) cannot run AVX2 at all, so every number below
comes from the project's own CI (`gh workflow run ci.yml`, run 37033080955,
`bench (amd64, ubuntu-latest)` job, 2026-10-02) on a real AMD EPYC 9V74,
confirmed flags: `avx avx2 avx512bw avx512cd avx512dq avx512f avx512ifma
avx512vbmi avx512vl sha_ni`.

## Confirmed current, with fresh real-hardware numbers

`GODEBUG=cpu.sha=off` (this core's actual target: AVX2 present, SHA-NI
absent — the comparison that matters, since stdlib would otherwise use
hardware SHA-NI and win trivially):

```
BenchmarkPBKDF2Sha1StdlibSequential   cpu.sha=off: 487.8-489.6 candidates/s
BenchmarkPBKDF2Sha1LaneHasherAVX2     cpu.sha=off: 393.7-394.9 candidates/s
```

AVX2 lane hasher is ~19-20% behind stdlib on this run — same direction, same
rough magnitude as the ~26% figure recorded on a different EPYC generation
previously. The problem is real and current, not stale.

Isolated diagnostic (schedule expansion vs. compression, same methodology
used to find and fix SHA-256/512's real bottleneck):

```
BenchmarkSHA1ScheduleExpansionScalarX16   1115-1127 ns/op  (16 lanes, scalar Go)
BenchmarkSHA1CompressAVX2GroupOnly        2139-2186 ns/op  (16 lanes, AVX2)
```

Compression costs ~1.9x more than schedule expansion for SHA-1 — the
opposite ordering from SHA-256 (schedule 762.9-768.8ns vs compress-only
214.6-214.7ns, 8 lanes) and SHA-512 (schedule 670.6-671.0ns vs compress-only
334.4-337.5ns, 4 lanes), where schedule expansion dominated and vectorizing
it is what won those two their real-hardware wins. **Confirms, with fresh
numbers rather than trusted prose: SHA-1's bottleneck is the compression
core itself**, consistent with the prior session's conclusion.

## Re-derived the register math from the actual generator (not assumed)

Read `sha1avx2_gen.py` end to end rather than trusting the prior summary.
Its own docstring and `round_block()` are precise: 5 state + 3 scratch = 8
YMM/chain, so the 16-YMM budget fits exactly **N=2** two independent 8-lane
chains, zero registers to spare. Every round costs 14 (parity), 15 (ch), or
16 (maj) vector instructions, of which **exactly 2 are `VMOVDQU`
register-to-register copies** — `new_a` into old `b`'s slot, `new_c` into
old `e`'s slot — because SHA-1's `b -> c` transition (`ROTL30(b)`) is a real
computation, not a free relabel the way MD5/SHA-256's round state updates
are. That's real, confirmed overhead (~13% of each round's instructions),
but it is NOT large enough by itself to explain a ~5x per-lane cost
difference against SHA-256's compression (214.6ns/8 lanes = 26.8 ns/lane vs.
2139-2186ns/16 lanes = 133.7-136.6 ns/lane for SHA-1) — there's a bigger
structural cost than the copies alone.

**That bigger cost: N=2 means the "16 lanes" figure is two separate 8-wide
chains' worth of instructions issued back-to-back in one call, not a
genuinely 16-wide SIMD operation.** A YMM register is 256 bits — 8 lanes of
uint32, full stop. Reaching 16 lanes with pure AVX2 structurally REQUIRES
running two chains (double the real instruction count), which is exactly
why this core interleaves two chains for latency-hiding rather than packing
wider — there is no wider AVX2 register to pack into.

## The one concrete new idea this spike surfaces: AVX-512

The CI runner that produced every number above **already has AVX-512**
(`avx512f avx512bw avx512vl` and more), and nothing in this codebase uses
it yet (checked: no `ZMM`/`AVX512` reference anywhere in `go_hashsmith`).
AVX-512's ZMM registers are 512 bits — genuinely 16 lanes of uint32 in ONE
register, not two chains. This would attack both costs identified above at
once:

1. **A true 16-wide single chain** replaces N=2's two-chains-of-8 — the
   instruction volume for "16 candidates" could plausibly halve relative to
   today's approach, not just get marginally tuned.
2. **32 ZMM registers instead of 16 YMM** removes the "zero spare
   registers" ceiling `sha1avx2_gen.py`'s own docstring documents as the
   reason N=2 has nothing left over — there may be room to avoid at least
   one of the two forced `VMOVDQU` copies per round with registers to
   spare, something structurally impossible in the current 16-YMM budget.

This is a genuinely different direction than "tune the existing AVX2 core
harder" — per the generator's own register-reuse derivation, that core is
already near-minimal for its instruction shape (3 scratch registers was
proven tight, not sloppy, during its own construction). Squeezing more out
of N=2 AVX2 has low expected payoff; AVX-512 is untried territory with a
real structural reason to expect more.

**Real tradeoff to weigh, not glossed over:** AVX-512 is less universally
available on real-world cracking rigs than AVX2 — this is a genuine
portability cost against a real hashcat/John comparison, where AVX2-level
hardware is closer to a safe baseline assumption. Any AVX-512 core would
need its own runtime CPUID gate and AVX2 fallback, mirroring how SHA-NI
detection already works here.

## Update 2026-10-03: the copy-elimination idea was tried, measured, and kept

The "rotating free-register pool instead of a fixed one" idea above turned
out to be directly actionable without touching the register budget at all
— see commit `34c7426`: `sha1avx2_gen.py` revised so `Ta`/`Tf` (which
already hold `new_a`/`new_c` by construction) simply become the next
round's `a`/`c` registers instead of being copied into the registers freed
by old `b`/`e`. Same 8 YMM/chain budget, N=2 still fits 16 YMM, zero new
registers — just better bookkeeping in a fully-unrolled static generator
that never needed the copy in the first place.

**Measured properly, not assumed.** Two CI runs immediately after showed
SHA-1 compression getting RELATIVELY worse against SHA-256/512's own
numbers on the same run — the opposite of expected — but those two runs
landed on a different EPYC model (7763) than the original baseline (9V74),
and SHA-256/512 themselves were measurably slower on 7763 too. Comparing
across different runs on different physical machines isn't rigorous
enough to separate a real regression from cross-model noise, so a
same-job, same-machine, same-input controlled A/B was built: the pre-fix
core extracted verbatim from git history under a throwaway name
(`sha1g16AVX2Old`), benchmarked in the exact same CI invocation as the
post-fix core. Result, AMD EPYC 7763, same run:

```
BenchmarkSHA1CompressAVX2GroupOnly       (post-fix)  2732-2781 ns/op
BenchmarkSHA1CompressAVX2GroupOnlyOld    (pre-fix)   2812-2855 ns/op
```

**The fix is real: ~1.5% faster, consistently, same machine.** Far smaller
than the 13% instruction-count reduction (2 of ~15 instructions/round)
might suggest — the most likely explanation is that modern AMD cores
already handle register-to-register `VMOVDQU` via renaming at
near-zero added latency, so removing it helps only at the margins (decode/
retire bandwidth), not execution ports. Kept — it's a real, free,
zero-risk win with full differential-test coverage — but it does not
meaningfully close the ~19-20% gap against stdlib on its own. The
AVX-512 question above remains the real lever, still undecided, still
the next session's call. (Throwaway A/B scaffolding and the temporary
CI benchmark-regex addition used to produce the numbers above were
removed in the same commit sequence, per their own stated purpose.)

## Disposition

The register-rotation micro-optimization above is shipped and kept — real,
measured, modest. The bigger question (AVX-512 vs. continued AVX2 tuning
vs. leaving the remaining gap documented-open, same disposition as scrypt)
is still the next real decision point, same as every prior AskUserQuestion
fork point in this project's history.
